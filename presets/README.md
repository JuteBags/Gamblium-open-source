# Presets

A preset is a JSON file the launcher lays over its built-in preset:

```json
{ "name": "...", "local_state": { "dotted.pref": value }, "preferences": { "dotted.pref": value }, "args": ["--switch"] }
```

`local_state` goes to `<user data>\Local State`, `preferences` to `<profile>\Preferences`.
Both are written only while Brave is closed.

```
gamblium launch --preset-file presets/debloat.json
```

| File | Use |
|---|---|
| `debloat.json` | Removes Brave's extras and prompts. Only removal, no taste: safe to lay over a profile someone already uses. |
| `new-profile.json` | Choices for a folder the launcher creates: search default, bookmarks bar, new tab colour. Never on an existing profile, where these are the user's own settings. |
| `theme-<scheme>-<dark\|light>.json` | Whole-browser theme from one seed colour. Generated by `branding/make_icons.py`; see `branding/README.md`. |
| `force-dark.json` | Darkens websites that only have a light design. Same as the launcher's `--force-dark`. Sites listed under "keep light" in the extension are left alone. |

## debloat.json

Tested on Brave 1.99.56 (Chromium 157), Windows 11, throwaway profiles, through
`gamblium launch`. After a launch every pref of both files is still set
(`docs/design/tools/verify.mjs`: 35 of 35 and 4 of 4).

### Sponsored images: what is and is not proven

Sponsored images are held off by `brave.brave_ads.sponsored.enabled` = false and,
on this machine, by the Rewards policy. No sponsored image appeared in the tests,
but they are rare, so this is not proof. If one ever shows up, set
`brave.new_tab_page.show_background_image` to false: that removes every background
image for certain, at the price of Brave's purple fallback gradient.

### Do not add these back

Brave 1.99 clears them at every start, so they do nothing:
`brave.new_tab_page.hide_all_widgets`, `brave.new_tab_page.show_branded_background_image`,
`brave.new_tab_page.show_sponsored_sites`, `brave.show_brave_rewards_button`,
`brave.today.intro_dismissed`, `brave.brave_ads.opted_in_to_search_result_ads`,
`brave.always_show_bookmark_bar_on_ntp` (now `bookmark_bar.visibility_state`), and in
Local State `brave.default_browser_prompt_enabled`, `brave.ad_block.cookie_list_opt_in_shown`.

### Policies (opt-in)

`debloat.json` also carries a `policies` section. The launcher writes it to
`HKCU\Software\Policies\BraveSoftware\Brave` only with `--apply-policies`, and
`gamblium policies --remove` takes it out again. Prefs hide buttons; policies
also remove the menu entries and settings sections, and the user cannot switch
them back on by accident.

| Policy | Removes |
|---|---|
| `BraveRewardsDisabled` = 1 | Rewards button, menu entry, settings, sponsored content |
| `BraveWalletDisabled` = 1 | Wallet button, menu entry, Web3 settings |
| `BraveVPNDisabled` = 1 | VPN button and menu entry |
| `BraveAIChatEnabled` = 0 | Leo button, sidebar item, context menu, settings |
| `BraveNewsDisabled` = 1 | News on the new tab page |
| `BraveTalkDisabled` = 1 | Talk card and sidebar item |
| `BravePlaylistEnabled` = 0 | Playlist |
| `BraveSpeedreaderEnabled` = 0 | Speedreader button and settings |
| `BraveWaybackMachineEnabled` = 0 | Wayback button on missing pages |
| `BraveP3AEnabled`, `BraveStatsPingEnabled`, `BraveWebDiscoveryEnabled`, `MetricsReportingEnabled` = 0 | Telemetry, not user-changeable |
| `PromotionsEnabled`, `PromotionalTabsEnabled`, `FeedbackSurveysEnabled` = 0 | Promo content, promo tabs, survey prompts |

Every name is in `docs/design/debloat/policy-names-brave-1.99.56.txt`, read from
`brave://policy`. The first six are already set machine-wide here, so only those
were seen working; the rest are untested as policies. Left out on purpose:
`TorDisabled` (Tor stays), `DefaultBrowserSettingEnabled` (it would also stop the
user making this their default browser), `BraveLocalAIEnabled` and
`ChromeVariations` (not measured). Cost: "Managed by your organization" shows in
the app menu and settings.

## new-profile.json

| Pref | Why |
|---|---|
| (no search pref) | Google is the default search engine, by the owner's decision (Nov 12 2026). It comes about by leaving `brave.search.default_version` unset (see point 4 below). Brave Search, DuckDuckGo and the others stay in the list under Settings, Search engine |
| `bookmark_bar.visibility_state` = 2 | No bookmarks bar with the "Import bookmarks now" line. Ctrl+Shift+B brings it back |
| `brave.new_tab_page.background` = solid `#0B1210`, `show_background_image` = true | Plain dark new tab instead of Brave's photos. The solid colour needs "Show background images" on |

All three were seen working in screenshots (`docs/design/debloat/new-tab-before-after.jpg`).

## New profile folders

Measured. The launcher now creates the `First Run` file itself (commit e279e16).
(The counts are from earlier versions of the file, with 43 and then 37 prefs.)

1. **A first run throws our profile prefs away.** When a folder has no `First Run`
   file, Brave copies its bundled `initial_preferences` over `Default\Preferences`.
   Result on a new folder: 36 of 43 prefs lost, welcome page shown.
2. **`--no-first-run` is not enough.** It works for that one start (37 of 37 kept)
   but does not create the `First Run` file. The next start without the switch, for
   example from a plain Brave shortcut, is a first run again: 30 of 37 prefs lost.
3. **Fix:** before the first start of a new folder, create an empty file named
   `First Run` in it. Then no switch is needed: 37 of 37 kept, no welcome page.
4. **Search engine:** with first run skipped, Brave treats the profile as an old one
   and makes Google the default search engine. That is the default Gamblium ships
   with, so nothing is set. (Setting `brave.search.default_version` to 35 would give
   Brave Search instead; an earlier version of `new-profile.json` did that.)
5. `--initial-preferences-file` is ignored by this Brave build, so we cannot hand it
   our own first-run file.

## What cannot be removed from outside

Seen on the debloated profile. These need a source fork, or stay.

| Still there | Where |
|---|---|
| The word "Brave" | Window title ("New Tab - Brave"), the app menu button's name, "About Brave", `brave://` addresses, "Search Brave or type a URL" |
| Brave lion | Shields button, new tab favicon, settings header, internal pages |
| "Sidebar" row (On / Autohide / Off) | App menu, even with the sidebar off |
| "New private window with Tor" | App menu (kept on purpose; the `TorDisabled` policy would remove it) |
| "Managed by your organization" | App menu and settings, because policies are in use |
| "Log in or create a Brave account" card, "Make Brave the default browser" | Settings, Get started |
| Brave's settings pages as a whole | `brave://settings` (Leo, Web3 and Brave Origin sections are hidden by policy here) |

Not tested: a machine without the `HKLM` policies. There, prefs hide the toolbar
buttons, but the Leo, VPN, Wallet and Rewards entries in the app menu and in
settings most likely need the same policies in `HKCU`.

## How to re-check

Needs Node 22+. Every script makes its own throwaway folder under the temp
directory, closes its browser when it ends (pass or fail) and deletes the folder.
None of them can be pointed at a real profile, and none brings a window to the
front.

```
node docs/design/tools/real.mjs <label> <out folder> presets/debloat.json presets/new-profile.json   # through gamblium launch
node docs/design/tools/verify.mjs presets/debloat.json <out folder>/<label>                          # did every pref stay?
node docs/design/tools/tour.mjs <label> <out folder> presets/theme-burgundy-dark.json                # six views of a theme
node docs/design/tools/forcedark.mjs <label> <out folder> presets/force-dark.json                    # five sites, forced dark
node docs/design/tools/menu.mjs <out.png> presets/debloat.json                                       # toolbar and app-menu inventory
```

`winshot.ps1` photographs the real window, toolbar included, even when it is
covered. `uia.ps1` and `uia-act.ps1` read and press Brave's own buttons through
UI Automation, without taking focus.
